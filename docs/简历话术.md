# 面经阁 · 简历话术与面试准备

> 用途：写简历项目经历 + 面试自我介绍/项目深挖时的话术底稿。
> 建议：简历上写「面试题库复盘系统」，面试讲清楚 1 个核心难点 + 1 个设计权衡即可，不贪多。

## 1. 项目概述

**一句话版（简历/自我介绍用）：**
独立设计开发的前后端分离面试复盘系统，覆盖题库管理、面试记录、统计分析、遗忘曲线复习与投递跟踪五大环节，Spring Boot 3 + Vue 3 + MySQL + Redis 技术栈，含 Markdown 导入解析、JWT 认证、单元测试等工程化实践。

**展开版（1 分钟项目介绍）：**
秋招刷题时发现「背了忘、忘了查、查不到当时为什么错」，于是做了一个给自己用的复盘系统：面试中遇到的所有题目按场次结构化记录（题目、得分、扣分点、现场回答），自动沉淀进题库；统计模块告诉我哪类题被问得最多、均分最低；复习模块按遗忘曲线自动排期，低分题自动进入复习队列，答上就延后、答差就提前；投递看板跟踪每家公司走到哪一轮。全部数据本地化，个人隐私数据不进仓库。

## 3. 难点与解决（面试深挖答案）

**Q：统计接口为什么用 Redis 缓存？怎么保证一致性？**
A：统计是读多写少的聚合场景，三张图每次都要 join 面试记录和题目表再聚合。方案是缓存结果 30 分钟 + 写时失效：题库/面试记录/导入/复习的**每一个写操作**之后主动删除缓存 key，下次读取重新计算。选「删除缓存」而不是「更新缓存」，因为更新需要重算一次聚合，删了让读方懒计算，逻辑简单且不存在双写不一致窗口；30 分钟 TTL 是兜底，防止漏删导致长期脏数据。缓存不可用时（Redis 挂了）读接口降级直查数据库，不影响主流程。

**Q：复习队列的 ZSet 是怎么设计的？Redis 数据丢了怎么办？**
A：member 是复习计划 id，score 是下次复习日期的 epochDay，今日任务 = 一次 rangeByScore(0, today) 搞定，天然有序、天然过滤，不用存结构化 JSON。Redis 本身是缓存不是主存储：启动检查 key 不存在就从 MySQL 全量重建，ZSet 为空自动过期删除 key 后同样会触发重建；所有 Redis 写操作都 try-catch，异常时记日志回退数据库查询，保证复习功能不因缓存故障不可用。

**Q：遗忘曲线间隔为什么是 1/3/7/15/30，×1.5 是什么意思？**
A：参考艾宾浩斯遗忘曲线的经典间隔，做成可配置项（设置页可改，2-10 档、逐档递增、1-365 天）。打卡规则是「答上 → 进下一档，但间隔 = 下一档标准间隔 × 1.5」，比如第 2 轮本来 7 天，答得好就 11 天后见——因为掌握得好的题不需要严格按曲线，延后复习节省时间；答差 → 降回上一档，把题重新排近。走完五档毕业归档，归档题如果重新入队会重置回第一档重新来。

**Q：Markdown 导入的解析器怎么做健壮的？**
A：解析器按「成绩总览表 + 题目明细段」两个区块用状态机逐行处理：总览表先建立题号索引，明细段按「第 N 题」对齐到同一题，字段按加粗标签（题目/你的回答/扣分点/参考答案）累积到对应字段，明细标题里的分数可以覆盖总览（支持「（修正后）」后缀）。关键设计：解析结果先展示预览页让用户修正（分类、是否答上、文本），确认后才落库；标题全等的题直接复用已有记录，避免题库重复。解析器配了单元测试覆盖多行回答、缺失明细段、修正分数这些边界情况。

**Q：状态机为什么不让自由跳转？**
A：投递流程的现实顺序是固定的（投递→笔试→一面→二面→三面→HR→Offer），自由跳转会弄脏统计数据（比如直接从投递跳到 Offer，趋势就不可信）。所以只允许「推进到下一个状态」或「标记已挂/已拒」，跳步直接报错，终态不可再流转。每次流转自动插一条时间线记录（from/to/备注），追进度只看时间线。

**Q：这个项目有测试吗？**
A：核心逻辑都有 Mockito 单元测试（31 个）：状态机的跳步拒绝/终态锁死、复习打卡的进档降档毕业规则、自动入队触发条件、Markdown 解析器的边界情况。业务规则集中测试，接口层用 Knife4j 手工验证过全流程。

## 4. 高频追问预案

- **为什么做这个项目？** 真实痛点：秋招刷题发现自己缺少体系，需要「被问过什么、错在哪、什么时候该再背一遍」的闭环，顺便把学到的技术串起来。
- **为什么选 Spring Boot 3 / MyBatis-Plus？** Spring Boot 3 是当前主流版本（JDK 21 生态），MyBatis-Plus 对单表 CRUD 场景开发效率高，复杂 SQL 不多，够用且简单。
- **为什么不用现成的复习软件（Anki）？** Anki 是通用卡片，没有「按面试场次记录现场表现」「按公司/岗位维度统计被问频率」这些面试场景特有的数据模型；自己写也能把简历上的技术栈全部落地。
- **难点在哪？** 不在 CRUD，在**规则设计**：复习排期规则、状态机约束、导入解析的健壮性，这些规则分散在多个模块且会互相影响（比如删除题目后复习计划怎么处理），把它们理清楚并用单测钉住，是这项目最花时间的地方。
- **如果用户变多怎么扩展？** 单账号是明确的范围裁剪（自用）；统计缓存已经按读多写少设计，横向扩展路径是 Redis 集群 + 读写分离，但当前量级没有必要。
